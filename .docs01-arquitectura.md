\# Arquitectura del laboratorio



\## 1. Descripción general



Este laboratorio implementará replicación en streaming de PostgreSQL entre dos máquinas virtuales con Ubuntu Server.



El servidor principal recibirá las operaciones de lectura y escritura. La réplica recibirá continuamente los registros WAL generados por el servidor principal.



\## 2. Objetivo



Diseñar un entorno que permita:



\* Replicar datos entre dos servidores PostgreSQL.

\* Comprobar la sincronización de los datos.

\* Simular la caída del servidor principal.

\* Promover manualmente la réplica.

\* Medir el tiempo necesario para recuperar el servicio.



\## 3. Componentes



| Componente              | Función                               |

| ----------------------- | ------------------------------------- |

| VirtualBox              | Ejecutar las máquinas virtuales       |

| Ubuntu Server 24.04 LTS | Sistema operativo de los servidores   |

| PostgreSQL 16           | Sistema gestor de base de datos       |

| OpenSSH Server          | Administración remota de las máquinas |

| Git y GitHub            | Control de versiones y documentación  |



\## 4. Máquinas virtuales



| Nombre       | Función                         | Dirección IP    |

| ------------ | ------------------------------- | --------------- |

| `pg-primary` | Servidor PostgreSQL principal   | `192.168.56.10` |

| `pg-standby` | Servidor PostgreSQL de respaldo | `192.168.56.11` |



Cada máquina virtual tendrá inicialmente:



\* 2 procesadores virtuales.

\* 2 o 3 GB de memoria RAM.

\* Disco virtual dinámico de 25 GB.

\* Un adaptador NAT para acceder a Internet.

\* Un adaptador de red solo-anfitrión para la comunicación entre los servidores.

\## 6. Flujo de replicación



1\. El cliente inserta o modifica datos en `pg-primary`.

2\. PostgreSQL registra las operaciones en los archivos WAL.

3\. Los registros WAL se transmiten a `pg-standby`.

4\. La réplica aplica los cambios recibidos.

5\. Se comprueba que la información exista en ambos servidores.



\## 7. Escenario de failover



Durante la prueba se apagará o detendrá el servidor `pg-primary`. Posteriormente, `pg-standby` será promovido manualmente para aceptar conexiones y operaciones de escritura.



El tiempo de recuperación se medirá desde la detección de la caída del servidor principal hasta que la réplica promovida pueda recibir consultas y escrituras.



\## 8. Alcance



La primera versión utilizará dos máquinas virtuales y failover manual. No se implementará inicialmente un sistema de consenso ni promoción automática.



Como mejora futura se podrá agregar un tercer nodo y herramientas como Patroni y etcd para automatizar el failover y reducir el riesgo de una situación de split-brain.
